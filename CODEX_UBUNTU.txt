PARCOURS UTILISATEUR IMPLEMENTE
1. Ouvrir le dashboard, se connecter avec un compte approuve.
2. Ouvrir Operations > Live map (/map), desactiver le mode Demo.
3. Choisir le monde correspondant a Gazebo (ex. warehouse-harmonic).
4. Dans Gazebo navigation, cliquer Choose on map puis cliquer sur la carte 2D,
   ou saisir X/Y en metres et Heading en degres.
5. Verifier la destination, puis cliquer Go to destination.
6. Voir la position ROS du robot, le retour Nav2 et la distance restante.
7. Cancel navigation demande l'annulation a Nav2. L'affichage attend le resultat.

ARCHITECTURE
Live Map React
  -> roslib / rosbridge WebSocket (port 9090)
  -> service /dashboard/navigation/submit
  -> nouveau noeud dashboard_navigation
  -> action Nav2 /navigate_to_pose
  -> commande du robot dans Gazebo.

Retour : TF map -> base_link + feedback/resultat Nav2
  -> /dashboard/navigation/state (std_msgs/msg/String contenant du JSON v1)
  -> roslib -> robot et etat affiches dans Live Map.

Gazebo execute la physique. Le navigateur affiche une representation SVG 2D ou
isometrique 3D du monde SDF. Il ne contient pas un moteur Gazebo et ne recoit pas
un rendu video Gazebo. Le decor peut etre approximatif ; seule la costmap Nav2
sert a verifier les destinations et Nav2 reste responsable de la navigation.

PERIMETRE ET LIMITES A PRESERVER
- Une base amr_x, un serveur de navigation, un monde actif a la fois.
- Le nouveau parcours est dans Live Map. La page Missions et son CRUD FastAPI
  restent des enregistrements de gestion ; leurs boutons ne pilotent pas Nav2.
  La navigation Live Map n'est pas enregistree dans PostgreSQL.
- Pas de pause/reprise Nav2 ajoutee : envoyer, suivre, annuler et resultat final.
- Pas de robot physique : le noeud refuse les destinations si use_sim_time=false.
- Pas d'arbitrage entre commandes externes RViz, teleoperation et autres noeuds.
  Pendant les essais, utiliser uniquement Live Map pour commander la base.
  Lancer Nav2 avec mission_server:=false pour eviter le serveur historique.
- Fermer l'onglet ou perdre le WebSocket ne stoppe pas automatiquement Nav2.
  L'interface l'indique. Annuler avant de quitter ; si la connexion est perdue,
  reprendre le controle dans l'environnement ROS/Gazebo.
- rosbridge reste celui du projet : pas d'authentification de commandes ajoutee.
  Usage de simulation locale, pas un service de controle pret a exposer sur Internet.
- Un seul but actif est accepte, y compris pendant l'attente d'acceptation Nav2.
- Un acquittement du service signifie demande recue, pas destination atteinte.
- Si un appel expire, son resultat est incertain : consulter l'etat avant de
  reessayer. Le frontend ne rejoue pas automatiquement les commandes.
- L'identifiant world_id est configure par l'operateur ; il ne prouve pas a lui
  seul que le bon monde Gazebo est ouvert. Verifier la configuration au lancement.

IMPORTANT : ALIGNEMENT DES REPERES
Le monde SDF de Gazebo et le repere map de Nav2 ne coincident pas necessairement.
Le noeud utilise TF map -> base_link, jamais /odom seul, pour localiser le robot.
Parametres world_offset_x, world_offset_y, world_offset_yaw : pose de l'origine
du repere map dans le monde SDF. Valeurs par defaut : 0, 0, 0 ; a verifier.
  position_world = rotation(world_offset_yaw) * position_map + offset_xy
Le but web est transforme par l'inverse avant envoi a Nav2.
L'orientation est en radians cote ROS ; l'interface saisit des degres.

Comparer la pose TF avec la pose reelle Gazebo a au moins deux emplacements.
Si les axes sont identiques : offset_xy = position_Gazebo - position_TF_map.
En cas de rotation, determiner aussi l'angle entre les reperes avant la translation.
L'origine du fichier YAML de carte est l'origine de la grille DANS map ; elle
n'est PAS automatiquement le decalage map-vers-Gazebo. Ne pas la recopier ici.
Passer les offsets mesures au lancement, par exemple avec les arguments
world_offset_x:=... world_offset_y:=... world_offset_yaw:=...
Ne pas annoncer l'alignement comme valide tant qu'il n'a pas ete mesure sur Ubuntu.

DIAGNOSTIC ROS
  ros2 node list
  ros2 action info /navigate_to_pose
  ros2 run tf2_ros tf2_echo map base_link
  ros2 topic hz /dashboard/navigation/state
  ros2 topic echo /dashboard/navigation/state --once
  ros2 service type /dashboard/navigation/submit
  ros2 service call /dashboard/navigation/cancel std_srvs/srv/Trigger '{}'

La passerelle refuse les buts si TF est absent/perime, Nav2 absent, costmap
absente/perimee, mauvais world_id, coordonnees invalides ou cellule inconnue/
occupee. Le seuil est 65 sur OccupancyGrid (-1, 0..100), pas 200.
Les configs Nav2 existantes publient la costmap complete. Si elles changent,
conserver always_send_full_costmap=true ou implementer aussi les mises a jour.
La carte SVG approximative n'est jamais utilisee comme carte de collision.
Une position cible libre peut quand meme etre inaccessible : c'est Nav2 qui
doit retourner un echec. Le frontend affiche le resultat recu, sans l'inventer.

VALIDATION A TERMINER SUR UBUNTU
Pour chaque essai, noter configuration, but, resultat, temps et observations.
A. Position : robot au meme endroit dans Gazebo, RViz, carte 2D et vue 3D.
B. But libre proche : service acquitte, navigating, mouvement, succeeded.
C. Detour autour d'un obstacle : trajet Nav2 et mouvement cohérents.
D. But occupe/hors carte/inconnu : refus explique, pas de nouveau mouvement.
E. But libre mais inaccessible : retour failed de Nav2, pas de faux succes.
F. Annulation en route : canceling puis canceled, arret du robot a verifier.
G. Double clic / deux clients : pas de remplacement du but actif par le gateway.
H. Couper rosbridge : commandes bloquees, position live retiree apres perte de
   connexion/donnees ; reconnexion, etat retrouve, aucun renvoi automatique du but.
I. Mettre Gazebo en pause : donnees perimees, nouvel envoi bloque apres 2,5 s.
J. Mauvais monde dans Live Map : nouvel envoi bloque.
K. Activer Demo : commandes interdites ; donnees explicitement illustratives.
L. Changer URL dans Settings : nouvelle connexion sans rafraichir la page.
